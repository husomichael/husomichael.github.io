Multi-vendor camera management

2026

Java 21 · Spring Boot 3.5 · PostgreSQL · Flyway · OAuth 2 · WebRTC

A greenfield service putting two camera vendors — whose auth models share almost nothing — behind one adapter interface. Adding the second vendor required no controller changes. Architect and primary author.

  • A required core, and defaults for everything else

    Vendors differ in what they can do at all. The required surface is only what both genuinely support; optional capability fails loudly and by name rather than returning null and surfacing as a mystery a layer higher.

  • Tenancy is decided, never inferred

    Account linking originally read the property from the logged-in session, and accounts landed on the wrong one. The rewrite parks credentials bound to nothing until a human explicitly binds them. Slower on purpose.

Resident internet: accounting and adoption

2025 — present

Java 21 · Spring Boot 3.5 · PostgreSQL · Flyway · Vue 3

The service behind a resident Wi-Fi product — what plans exist, who subscribes, what they owe, and what the property earns. Where I went from writing my first Spring service to owning its accounting layer.

  • Cache what you don't own; read what you do

    Listing networks meant ~13 sequential vendor calls on every page request, because the sort and filter fields lived in the vendor's API. A 30-second cache of only the vendor's half means the list can show a stale label, never a stale row.

  • Absence is not zero

    Adoption can't be reconstructed from current state, so it's recorded daily. A missing day reads as "not measured," never 0% — and the API returns counts rather than rates, so the client never adds two rounded numbers.

The app property staff use to run a building: access control, key fobs, thermostats, payments and unit sync. 761 commits over four years — the most surface area, and the most useful failure stories.

  • State machines instead of boolean flags

auto-log In development

Spring Boot 4 · Java 21 · Vue 3 · PostgreSQL · Flyway

A garage and vehicle maintenance log, built for my fleet of Japanese imports. The import constraint drove nearly every interesting decision in it.

  • Odometer units belong to the car, not the user

    Five of mine read kilometres while their history is in miles. Every reading stores what the cluster displayed alongside a generated miles column, so cost-per-mile stays comparable across a mixed garage.

  • The log has two audiences

    Purchase price, import duty and standing costs are private. A buyer's history sheet is built so those are structurally excluded — the disclosure boundary lives in the schema, not a checkbox someone can forget.

  • Reminders are rules, not records

    A rule stores no "last done" date, because one rule can cover the whole garage. The anchor is the newest linked maintenance record on that vehicle — so logging the work is what satisfies the reminder.
