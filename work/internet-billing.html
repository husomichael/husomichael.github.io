Resident internet: accounting and adoption

Java 21 · Spring Boot 3.5 · Spring Data JPA · PostgreSQL · Flyway · MapStruct · Testcontainers · Vue 3

The service behind a resident Wi-Fi product — what plans exist, who is subscribed, what they owe, what they paid, and what the property earns. This is the repository where I went from writing my first Spring service to owning its accounting layer, and where I design the endpoint against the screen that consumes it.

Span
2025 — ongoing
Role
Feature owner across the stack — the endpoint, the migration, the tests, the API docs, and the SPA that consumes it
Scale
176 authored commits over 15 months
Talks to
A network-orchestration service, an authoritative locations API, payment processing, a resident mobile app and a staff SPA

How I entered a stack I hadn't shipped before

I hadn't written production Java before this. The approach was deliberate and it's the honest answer to "how do you learn a new stack": a throwaway spike repo first, to make the framework's shape familiar without any business logic riding on it. Then, in the real service, the cross-cutting foundations — a global exception handler, structured JSON logging, and error handling for the outbound clients. I made failures legible before I added features. Business logic came third.

Cache what you don't own; read what you do

Listing a property's networks meant crawling an upstream service — roughly 13 sequential HTTP calls for a large property — on every page request. The obvious fix, pushing paging and sorting into SQL, was unavailable: the fields the list sorts and filters on (name, type, enabled state, security type) live in the upstream service, not in our database. You cannot page in SQL on fields you do not own.

The fix was a per-property, 30-second, in-memory snapshot of that crawl — with a boundary drawn deliberately.

DecisionReasoning
Cache only the fields we don't own Every field the service owns — ids, relationships, timestamps — is read fresh from the database on each request. So list membership is always correct. Only display values can lag, and only by 30 seconds.
TTL measured from crawl completion, not crawl start A multi-second crawl would otherwise eat its own lifetime, or expire the instant it finished. One commit exists purely for this.
30 seconds, not 5 minutes Long enough to collapse a burst of page navigations into a single crawl; short enough that a staff member who renames a network sees it within one refresh.
A read that never triggers a load Lets a caller with a cheaper path reuse a crawl someone else already paid for, without causing one itself.
Opportunistic purge, no sweeper thread Simpler — and documented as opportunistic precisely so nobody assumes a bounded memory guarantee that isn't there.
The cost, named

It's per-pod and in-memory, so N pods do N crawls, and there's no invalidation on write. Both are acceptable at this scale, and both are things I'd rather say first than be asked. A shared cache would cut the duplicate crawls at the cost of an operational dependency — a deliberate deferral, not an oversight.

The short version

"The list's sort and filter fields came from a vendor API, not our database, so we had to materialise the whole set to page it correctly. I cached the vendor half for 30 seconds and kept our half live — which means the list can never show a stale row, only a stale label."

One ledger from three tables

Payments, invoices and credit memos live in separate tables. The UI needed a single chronological feed per property, with unit, building and resident context on every row — correctly ordered and paginated across all three. That ordering belongs in SQL, not in application code, so it became a database view: a union over the transaction types with synthetic prefixed ids, then a lateral subquery that picks the single best-matching lease per transaction by date range.

  • Won: one query, one sort, one pagination. The application never merges three result sets in memory and never sorts a page it assembled itself.
  • The bug it was designed against: a location with several historical leases produced duplicate rows. The lateral pick exists specifically to collapse that.
  • Cost: a meaningful part of the domain is now written in SQL — fast, and invisible to anyone reading only the Java. It also took four migrations to settle, which is a fair criticism: the view's column set should have been driven from the UI's actual needs in one pass rather than discovered over four.

The part I'd want you to notice: the first version resolved unit and building with a lease-based heuristic. A commit the following day replaced it with the authoritative locations API. I shipped the heuristic, saw it was wrong in principle rather than in practice, and replaced it before it calcified — and naming it a heuristic in the commit is what made replacing it easy.

Absence is not zero

Adoption — what share of occupied units bought internet — has no history in a transactional schema. You can only ever compute today. So a scheduled job records a row each day, and the interesting design work was making absence unambiguous.

DecisionReasoning
A recorded snapshot, never a computed backfillOccupancy history can't be reconstructed from current state. A missing date means the job didn't run — explicitly not 0% adoption, and the API documentation says so in as many words.
The job is pinned to UTC"Which day is this" must not depend on a pod's locale.
Window derived from an injected clockTests assert against the same clock the code reads, so nothing is flaky by time of day.
Counts returned, never ratesThe client divides. Two rounded rates cannot be added; two counts can.
The measured window is returned in the responseThe UI's footer names the window the number was actually measured over, rather than restating a constant that might quietly drift out of sync.
The short version

"Adoption is a point-in-time fact the schema can't reconstruct, so we record it daily. The interesting constraint was making absence unambiguous — a missing day has to read as 'no measurement', never as 'zero'."

Error responses are part of the contract

Controllers bubble into one global exception handler rather than catching locally. Payment failures get a failure-type classification with its own handler and documented examples, rather than collapsing into a generic 500 — so a client can branch on why a payment failed. The API examples are pinned to the actual responses, so the docs can't drift silently.

The short version

"Classifying payment failures meant the mobile app could tell a declined card apart from an outage. That's a product difference, not a logging one."

Smaller calls worth having ready

  • 409, not a silent success, on deleting a plan with active subscribers. Refuse destructive operations with state attached rather than cascading.
  • A default plan created when a network is provisioned — but only after checking one doesn't already exist. Idempotency on a side effect.
  • One resource, one filter. Active-only and soft-delete filters on the existing subscriber endpoint rather than a second, parallel "archived" endpoint.
  • Timestamps normalised with an explicit timezone on ingest, rather than trusting an upstream service's format.
