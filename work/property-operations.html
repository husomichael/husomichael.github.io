Four years on one property-operations app

Vue 3 · TypeScript · Pinia · Vite · Vitest · Playwright · Unleash · vee-validate + Zod

The web app property staff use to run a building: issue and revoke access, assign key fobs, configure thermostats, take payments, suspend a delinquent unit's Wi-Fi, and keep unit data in sync with the system of record. 761 authored commits over four years — which makes it the project with the most surface area and, more usefully, the most honest failure stories.

Span
2022 — 2026
Role
Feature owner end to end — design file to feature flag to release, including backend routes when nobody else would add them
Integrations
Access control, thermostats, cameras, payments, and three property-management systems
Team
Small front-end team on a shared Vue app over a PHP and NestJS backend

A state machine, because the states kept multiplying

A USB fob scanner sits on the leasing-office desk. Staff scan an unknown key fob and the app tells them whose it is. There's no push channel from the hardware, so the browser polls. The flow is a modal whose entire behaviour is one status enum in a store — ready, loading, assigned, available, lost, error, not-found, no-scanner-detected, plus two in-flight action states. Each status renders a different child component, and every terminal state has an escape hatch that opens a support chat with a pre-filled message.

  • Won: impossible states became unrepresentable. Adding no-scanner-detected late was one enum member, one component, one branch — not an audit of boolean combinations.
  • Cost: transitions live in the store, so reading the flow means reading the store rather than the template. A newcomer can't see the state machine from the component.
The short version

"I modelled the flow as a state machine rather than a set of flags, because the states were genuinely exclusive and we kept discovering new ones. The interesting part isn't the polling — it's that the state space was discovered incrementally, and this design made each discovery additive instead of a refactor."

Bounded attempts, not a wall-clock timeout

The first version gave up after a 60-second timeout. That was replaced with polling that gives up after a fixed number of attempts. The failure became deterministic and testable, and the user gets a specific message instead of a hang — a wall-clock timeout races the request; an attempt count doesn't, and it composes with retries. The trade is latency: with no push channel, a real scan can still take up to the full poll window to appear.

The migration I'd run differently

Roughly 90 components were converted from the Options API to the Composition API, alongside a move from Vuex to Pinia and Webpack to Vite. It ran as a long-lived branch over six weeks while feature work continued on main. It shipped, and it was the wrong call.

The commit log shows the cost directly: a dense run of merges from main through two months, and several features implemented twice. The alternative — an incremental migration behind the framework's compatibility build, converting components as they were touched — was available.

The short version

"We took the big-bang branch because the state-library and build-tool changes were hard to do halfway. It worked, but the merge tax was larger than the conversion work, and I'd push much harder for the compat-mode path now."

Two levels of gating, for two different questions

Rollout and entitlement are different questions, and they got different tools: feature flags for rollout, per-building features from the backend for entitlement, and superadmin checks for anything destructive. Manual Wi-Fi suspension — a feature that cuts a resident's internet — shipped behind all three.

  • Won: a genuinely destructive feature could ship dark, be enabled for one property, and be pulled without a deploy.
  • Cost: two mechanisms that are easy to confuse. The resulting bug class was always identical — reading an asynchronously-resolved flag before it resolved, which renders the disabled state for a frame.

The bug class that kept recurring

Thermostat automations could be linked to a unit or to a shared space — a gym, a clubhouse. Three separate tickets in a row (spaces not being added, deletion failing, deletion of spaces failing) had one root cause: two entity kinds squeezed into one list without a discriminator. The fix was an explicit union type covering both.

The short version

"Two things that looked alike in the UI were modelled as one thing in the code. We paid for it three times before naming the union explicitly."

That's the same shape as the tenancy bug in the camera service, and it's the through-line I'd point at across all of this work: every serious bug in four years was something inferred that should have been stated.

Correctness of time

A thermostat schedule set for 8am must mean 8am in the building, not in the staff member's browser. Conversion was standardised into shared utilities and applied at the display edge, and appending the timezone label to displayed times ended a recurring class of support ticket.

The cost, named

Converting at the display edge means a wrong value can still travel through the app untouched. Normalising on ingest would have been stricter. The building's timezone is the domain timezone — we standardised the conversion but put it too late in the pipeline.

Levers for support, and what they cost

Rather than chase every sync failure with a property-management system, the app grew superadmin-only escape hatches: sync now, untie a tenant link, re-sync a single unit. Support could resolve a stuck property in minutes instead of filing a bug, and it shipped in days rather than a quarter.

The cost, named

It's a manual workaround that let the underlying sync stay unreliable, and it added a privileged code path that has to be gated correctly everywhere it appears. I'd still build the lever first — but I'd time-box it explicitly, because otherwise it quietly becomes the permanent answer.

Letting integrations fail independently

With this many third-party systems behind one screen, the important decision was blast radius. One commit exists purely to let an access-control vendor's calls fail separately, because an outage at that vendor was taking down the entire access view. The generalisable point: the app grew a defensive layer per vendor, and independent failure was designed in rather than discovered.

The inheritance was real

The first month was spent deleting: unused routes across fourteen service files, dead controllers, directives and views in a six-year-old AngularJS app, and about twenty dependency CVEs closed one commit at a time. Unglamorous, and the best possible introduction to a codebase — you learn where the bodies are by carrying them out.
