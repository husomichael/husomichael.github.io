Multi-vendor camera management

Java 21 · Spring Boot 3.5 · Spring Data JPA · PostgreSQL · Flyway · OAuth 2 · WebRTC · AWS Cognito

A greenfield service giving one product a single camera API across two vendors whose auth models have almost nothing in common. I designed it and wrote most of it. Adding the second vendor required no controller changes; the interesting work was deciding what the two vendors genuinely share — and what a service should refuse to infer.

Span
2026 — ongoing
Role
Architect and primary author, backend and front end
Scale
67 of the repository's 171 commits; the architecture, the README and the scheduler standard are mine
Vendors
Eagle Eye Networks (OAuth 2 authorization code) and Ring (app-store linking, WebRTC)

The constraint that shaped everything

The two vendors are not variations on a theme. Eagle Eye is a textbook OAuth 2 authorization-code flow, except the API base URL is region-specific and only discoverable after authentication. Ring is app-store linking: Ring calls us first, there is no consent screen we control or redirect the user to, and live video arrives as a WebRTC WHEP handshake rather than a stream URL you can put in a video element.

Their shared surface is close to the single sentence "has cameras." That was the real design problem — not writing two integrations, but deciding how small the honest common abstraction actually was.

The shape

A CameraVendorAdapter interface plus a CameraVendorRegistry — Strategy and Registry together. Adding a vendor means implementing the interface and annotating it as a component; the registry collects every adapter the framework finds and maps it by vendor. The controller never learns a vendor's name.

CameraController │ ▼ CameraVendorRegistry ─┬─▶ RingAdapter ──▶ Ring API └─▶ EagleEyeAdapter ──▶ Eagle Eye API resolved by vendor enum — the controller never learns a vendor name adding a vendor: implement the interface + annotate. no controller change.

A required core, and defaults for everything else

The interface splits in two. A required core every vendor must implement — generate an auth URL, redeem a code, refresh, revoke, list cameras, resolve the base URL — and default methods for anything a vendor might simply not do.

DecisionReasoning
Required core, optional defaults The shared surface stays small and honest. A vendor without event history returns an empty list rather than being forced to fake a capability it doesn't have.
Unsupported streaming throws, naming the vendor Fails loudly and specifically at the one place it matters, instead of returning null and becoming a mystery two layers higher.
Base-URL resolution lives in the adapter Eagle Eye needs a per-client base URL discovered after auth; Ring's is fixed. Making it an adapter concern kept region routing out of the service layer entirely.
Base URL passed in, not re-resolved Automated review caught a redundant round trip. An explicit parameter, one fewer HTTP call per listing.
The cost, named

Six of the interface's ten methods are default. That ratio is fine for two vendors and a smell at four — it says the abstraction is covering two things that aren't quite the same shape. A third vendor will either fit cleanly or force a split into capability interfaces, and I'd split rather than widen the base.

The design that was wrong in production

The first version of Ring account linking inferred an account's property from the logged-in session. Accounts landed on the wrong property. This is the bug I'd lead with in any conversation about failure, because the fix removed an inference rather than adding a check.

The rewrite split linking into three explicit moments:

1. Authenticate Ring calls our callback; tokens land in a staging table, bound to no property at all. 2. Claim The logged-in user's email is written onto the pending record — first writer wins — so support can see who started it. Still bound to no property. 3. Bind Support picks a pending record and a property. This is the only step that touches the accounts table.

The rule is stated directly in the code's documentation: the property is decided exclusively at bind time, never inferred from the ambient session — because that inference was the source of accounts landing in the wrong place. Supporting details: the pending row is locked on bind and consumed by id rather than flagged, the claim is atomic and null-safe, and a soft-deleted account is revived only when it is genuinely the same vendor account.

The cost, named

A human is now in the loop on every link. It is slower on purpose, and it does not scale without eventually automating the bind. That was the right trade for correctness on a tenancy decision, and it's a known bottleneck rather than an oversight.

The short version

"We were inferring a tenancy decision from session context, and it silently attached customer accounts to the wrong property. The fix was to stop inferring — make the binding an explicit, auditable action, with the credentials parked unbound until someone decides."

Live video without a media plane

For Ring live video the browser creates an SDP offer, the backend forwards it to Ring's WHEP endpoint, and the answer comes back so that media flows browser-to-vendor directly. The service brokers the handshake and never touches the media itself.

  • Won: no media servers, no bandwidth cost, no scaling problem. The backend handles a couple of small HTTP requests per viewing session.
  • Cost: no ability to record, transcode or observe the stream, and a browser that navigates away without closing leaks a session on the vendor's side — so the lifecycle is explicit, created and closed.
  • On the front end: a single composable owns the whole WebRTC lifecycle for both the grid tile and the detail view, with viewport gating so off-screen tiles don't hold open streams.
The short version

"We broker the handshake and stay out of the media path. That's the whole reason live video costs nothing to scale, and the price is that we can't record or inspect it."

Exactly-once scheduled work, without new infrastructure

Token refresh runs nightly and must run exactly once across every running pod. Rather than add a coordination dependency, the lock is a database row: insert-on-conflict-do-nothing, then a conditional update that only succeeds where the existing lock has expired. The owner is hostname plus a UUID, and a lock-at-most-for ceiling means a crashed pod's lock expires on its own.

  • Rejected: a leader-election dependency, or designating a singleton pod. Both add operational surface to solve a problem the database already solves.
  • Cost: a rolling deploy mid-job can leave the lock held until the ceiling expires. That makes the ceiling a correctness parameter, not a tuning knob — which is exactly the kind of thing that needs writing down.
  • The artifact: I wrote the scheduler-ownership standard as a document in the repo, so the next person adding a scheduled job follows the pattern instead of rediscovering it.

Security in an integration

  • OAuth state signed with HMAC-SHA256 plus a nonce — the state parameter is the CSRF defence in an OAuth flow, so it has to be signed, not merely random.
  • The callback endpoint's auth bypass narrowed to that exact path after a review round. A prefix bypass is an open door.
  • postMessage origin validated against a configured origin rather than a wildcard.
  • Vendor tokens stored server-side and never sent to the browser.

What I'd tell you before you asked

  • Reading live means the vendor's uptime is our uptime. Cameras are deliberately not mirrored into our database — a minimal anchor row exists only to hang our own preferences off, and the camera list is read from the vendor every time. There's nothing to reconcile and nothing to go stale, and the price is no degraded mode.
  • The interface is one vendor away from needing a split. See the default-method ratio above.
  • Documentation was scoped as real work, not cleanup. All 24 public operations carry summaries, descriptions and corrected error responses, and every failure variant on the token exchange is documented. If an endpoint is reachable from the internet, its failure modes are part of its contract — that's the difference between a partner integrating in a day and filing a ticket.
